# Project Overview — 2026-06-18

## Executive Summary
AHG Unlocker is an Electron + React desktop tool for installing unlocked Steam games via manifest injection (176K+ games, 97 mirror repos). It has a sophisticated dark gaming UI with Framer Motion animations, Zustand state management, and a multi-tier image cache. The codebase is largely healthy with a clean build, but App.tsx remains a god component (3478 lines), TanStack Virtual scrolling is installed but unused, and several UI/settings/layout areas are ripe for focused improvement.

## Architecture

### Layers
- **Electron main** (`electron/main.cjs`, 6468 lines) — IPC handlers (98 exposed), manifest repo operations, DepotDownloader, license system, Discord RPC
- **Preload bridge** (`electron/preload.cjs`, 391 lines) — contextBridge API surface
- **React frontend** (`src/`) — 11 pages, 50 components, 14 Zustand stores, 20 hooks, 8 services
- **Python backend** (`bridge/`, `backend/`) — JSON-RPC bridge, FastAPI server
- **C# core** (`core/`) — Steam manifest scanning, registry ops (secondary)

### Key Components
- **Pages**: HomePage, BrowsePage, LibraryPage, SettingsPage (675L), FixesPage, + 6 more
- **Hero**: HeroSection + FeaturedCarousel (home) with auto-rotate
- **Cards**: GameCard (grid/list), BentoCard, LibraryCard, PortraitCard, FixGridCard
- **Stores**: gameStore (333L), uiStore, settingsStore (117L), userStore, installStore, modalStore, discordStore, + 7 more
- **Image Pipeline**: imageCache.ts (787L) — generational LRU (hot 500 / warm 1000 / cold 500), IndexedDB persistence, WebP conversion, LQIP blur-placeholder, 3-tier priority prefetch, CDN fallback racing (7 hosts × 2 paths × Promise.any)

# High-Impact Feature Suggestions

## Performance — Image Fetching

### 1. Virtual Scrolling — Activate TanStack Virtual Across All Grid Views
- **What**: Replace naive rendering with @tanstack/react-virtual in BrowsePage, LibraryPage, FavouritesPage, and all grid views. Currently `M1` shows TanStack IS in dependencies but NOT used in any page except BrowsePage's virtualizer (which only calculates coverHeight).
- **Why**: With 176K games, rendering all grid items causes DOM bloat and scroll jank. Virtual scrolling renders only visible + overscan rows (~30 DOM nodes vs potentially hundreds).
- **Impact**: High — directly addresses the scroll 60fps performance budget
- **Effort**: Medium
- **How**: Wrap existing grid CSS (repeat + auto-fill) in a `useVirtualizer` wrapper. Each page's grid becomes a virtualized list of rows, each row containing the existing responsive column layout. The `useImagePrefetch` hook already exists and can be wired in.
- **Prerequisites**: None

### 2. Service Worker for Image Caching (Cache API instead of IndexedDB)
- **What**: Register a Service Worker that intercepts image requests from Steam CDN hosts and serves them from the Cache API. Replace the IndexedDB blob storage with `caches.open('ahg-images')` and native `Cache-Control` management.
- **Why**: IndexedDB is asynchronous, needs JS deserialization (ArrayBuffer → Blob → ObjectURL), and blocks the main thread during read/write. The Cache API is purpose-built for HTTP responses, works natively in the fetch pipeline, and avoids the Blob URL overhead (no revoking needed).
- **Impact**: High — eliminates IndexedDB serialization cost, reduces main-thread blocking, simpler eviction via cache space
- **Effort**: Medium
- **How**: Register SW that `oninstall`/`onactivate` caches active image responses. The SW `onfetch` handler matches against Steam CDN patterns (`steamstatic.com`, `akamai`), serves from cache or network. The existing `loadGameImage` remains as a fallback for non-Steam images (SteamGridDB, local).
- **Prerequisites**: Service Worker registration in index.html, test in Electron context

### 3. Image CDN Health & Race Optimization
- **What**: Profile which CDN hosts resolve fastest from the user's location and reorder FALLBACK_HOSTS accordingly. Cache the fastest host per session. Currently `loadGameImage` tries 7 CDN hosts × 2 paths = 14 URLs per file type via `Promise.any`, which is 14 simultaneous TCP connections per image.
- **Why**: On first load (no cache), the app fires up to 14 simultaneous connections per image — and with 30+ images visible, that's 420+ concurrent connections. CDN race is wasteful. Picking the fastest host reduces connections by 14×.
- **Impact**: Medium — network efficiency for uncached images, faster first-load image population
- **Effort**: Small
- **How**: Add a CDN latency check on app startup: fetch a 1px gif from each host, measure response time, sort hosts, store in session preference. Use only top 2 hosts instead of all 7. Add TTL-based recheck.
- **Prerequisites**: None

### 4. Progressive Image Loading with LQIP Blur-Up
- **What**: Ensure LQIP (Low-Quality Image Placeholder) is rendered immediately as a blur placeholder for every game card before the full WebP image loads. The LQIP system already exists (`getLqipData()`, `setLqipMemory()`) but is not wired into all card components — many show nothing or a generic gradient placeholder.
- **Why**: LQIP gives users a perceptual instant-load experience (1-2KB vs 50-200KB full image). Gap analysis: GameCard, LibraryCard, GenreRow, BentoCard all show generic gradient skeletons instead of actual LQIP blur-ups.
- **Impact**: High — perceived load time improvement, makes scroll feel instant after first pass
- **Effort**: Small
- **How**: Audit all card components to replace `placeholderGenerator` (solid gradient) with `getLqipData()` → backdrop-blurred `<img>`. Wire the LQIP into the `useLazyImage` IntersectionObserver so the blur-up transition is smooth. The LQIP data is already cached alongside the full image in IndexedDB.
- **Prerequisites**: None

### 5. Image Prefetch on Home Page Hero Rotate
- **What**: When the HeroSection auto-rotates (6500ms), prefetch images for the upcoming 3 featured games so they're in the hot cache before they appear. Currently, hero rotation triggers a new image load on each cycle.
- **Why**: Eliminates the ~200-500ms visible image load gap during hero rotation. The prefetch queue already exists (`queuePrefetch` + `PriorityQueue`) but none of the hero components use it.
- **Impact**: Medium — eliminates hero image pop-in during auto-rotation
- **Effort**: Small
- **How**: In HeroSection, on each `featuredGame` change, call `queuePrefetch()` with MEDIUM priority for the next 3 games' header images. The LQIP blur-up will show immediately and the full image appears when ready.
- **Prerequisites**: LQIP wiring from suggestion #4

## Core Features

### 6. Download Queue — Visual Management Panel
- **What**: Build a proper download queue UI panel (sidebar panel or modal) showing queued, in-progress, and completed downloads with progress bars, speed, ETA, pause/cancel/retry controls. The `downloadStore`, `installQueueStore`, and `installProgressStore` exist but there's no dedicated queue UI — only the per-install `DownloadProgressModal`.
- **Why**: Users installing multiple games have no visibility into queue state, order, or progress beyond one-at-a-time modals. A queue panel enables batch Install All, reorder, pause/resume — high value for power users.
- **Impact**: High — directly improves the one-click-install north star for batch operations
- **Effort**: Medium
- **How**: Extract the progress display from `DownloadProgressModal` into a reusable `DownloadQueueItem` component. Build a `DownloadQueuePanel` that renders a virtual list of queue items (using TanStack Virtual). Wire into existing `installQueueStore` actions. Integrate as a sidebar quick tool.
- **Prerequisites**: Ensure `installQueueStore` has pause/cancel/reorder actions

### 7. Game Collections / Smart Lists
- **What**: User-created game collections + auto-generated smart lists (e.g., "Unplayed", "Recently Updated", "Genre: RPG", "DLC Available"). Currently only basic Favorites exist.
- **Why**: With 176K games, users need organizational tools beyond a single Favorites list. Smart lists surface games the user might have forgotten.
- **Impact**: Medium — differentiator from basic Steam library tools
- **Effort**: Large
- **How**: Extend `userStore` with `collections: Map<string, string[]>` and `smartLists: Map<string, FilterCriteria>`. Add a Collections list to the sidebar. Build a collection management modal. Smart lists auto-populate via the existing game filter system.
- **Prerequisites**: None (collections are purely frontend state + persistence IPC)

### 8. Installed Game Status — Dynamic Badge & Library Sync
- **What**: Show real-time install status badges on all game cards (Installed/Not Installed/Updating/DLC Only). Sync installed game list from Steam on app launch via IPC. Currently the install status is loaded once and may drift if the user installs/uninstalls outside the app.
- **Why**: Users need to know at a glance what they already own. Stale install data causes confusion ("I already installed this but it still shows the Install button").
- **Impact**: High — core UX requirement for a game manager
- **Effort**: Small
- **How**: Enhance the IPC handler `getInstalledGames()` to check Steam library folders via manifest scan (C# core or direct Steam library parsing). Add a periodic sync (every 60s or on app focus). Wire a small colored dot/badge into GameCard. The `installedGames` array already exists in the store.
- **Prerequisites**: Steam library folder detection in main process

## UI Improvements

### 9. App.tsx Decomposition — Phase 3 (BLOCKED)
- **What**: Extract remaining inline JSX in App.tsx into standalone components. Currently 3478 lines, 15 modals already extracted. Remaining: inline game card rendering, inline modal logic, inline handler definitions.
- **Why**: God component makes the codebase hard to navigate, causes unnecessary re-renders (all 3478 lines re-execute on any state change), and blocks any meaningful refactoring. DECISIONS.md D001 blocks this without user confirmation.
- **Impact**: High — enables all subsequent UI work, improves dev speed, reduces re-renders
- **Effort**: Large (but one-at-a-time per D001)
- **How**: One extraction per build-verify cycle. Start with the smallest inline fragment (e.g., inline game card in the all-games grid → replacement with `<GameCard>`). Build-verify after each.
- **Prerequisites**: **User confirmation** (per DECISIONS.md D001)

### 10. Settings Page Decomposition
- **What**: Break SettingsPage.tsx (675 lines) into reusable tab components. Currently all 5 tabs (General, Appearance, Performance, AHG Tools, About) are in one file with inline JSX for each.
- **Why**: 675 lines with 5 independent tabs violates the 250 LOC ceiling. Each tab can be a standalone component, testable and editable independently.
- **Impact**: Medium — improves maintainability, reduces SettingsPage re-renders
- **Effort**: Small
- **How**: Extract each tab panel into `src/pages/settings/` directory: `GeneralTab.tsx`, `AppearanceTab.tsx`, `PerformanceTab.tsx`, `AhgToolsTab.tsx`, `AboutTab.tsx`. SettingsPage becomes a thin shell with tab navigation.
- **Prerequisites**: None

### 11. Consistent Skeleton / Loading State System
- **What**: Unify all loading states across pages into the existing `HomePageSkeleton` pattern. Currently: HomePage has a dedicated skeleton, BrowsePage shows inline spinners, LibraryPage shows nothing, FixesPage shows inline spinners.
- **Why**: Inconsistent loading states look unfinished. A unified skeleton system with LQIP blur-placeholders and shimmer animations (already defined in DESIGN.md) creates a polished, premium feel.
- **Impact**: Medium — polish and consistency
- **Effort**: Small
- **How**: Create a `PageSkeleton` component that accepts a layout preset (home/browse/library/fixes) and renders the correct shimmer placeholder grid. Replace all `loading ? <Spinner/> : ...` patterns with `<PageSkeleton preset="browse"/>`.
- **Prerequisites**: LQIP system (suggestion #4) for image placeholders

### 12. Search UX Overhaul
- **What**: Enhance the SearchBar with inline results dropdown, recent searches, keyboard navigation, fuzzy highlighting of matched characters. Currently search is a simple input that filters `games` via the Web Worker, with results shown in the main game grid.
- **Why**: Search is the primary discovery mechanism for 176K games. An inline dropdown with instant results, recent searches, and keyboard nav makes discovery feel as fast as Spotlight/Alfred.
- **Impact**: High — directly impacts the core user flow (find game → install)
- **Effort**: Medium
- **How**: Build a `SearchDropdown` component that appears below the SearchBar, showing top 10 live results with name, genre badges, and install status. Wire `<kbd>` navigation. Persist recent searches in `uiStore`. Highlight match characters using `<mark>`.
- **Prerequisites**: None (Web Worker and prefix trie already in place)

## Settings

### 13. Image Cache Management in Settings
- **What**: Add a Settings panel to view cache stats (size, entry count, hit rate) and clear the image cache. Currently there's no UI for cache management — the `cacheSize` state exists but appears to show only `'0 MB'`.
- **Why**: Users with limited disk space need to manage the IndexedDB image cache (can grow to 100MB+ with 2000 cached WebP images). A clear-cache button is the minimum viable UX.
- **Impact**: Low-Medium — quality-of-life for power users
- **Effort**: Small
- **How**: Expose `getCacheSize()` IPC handler that reads IndexedDB `cachedAt` entries. Add a "Storage" sub-tab in Settings → Performance or AHG Tools. Show chart of cache by game count / MB. Add "Clear Image Cache" button with confirmation.
- **Prerequisites**: None

### 14. Performance Profiling Settings
- **What**: Add a Performance tab with toggles for: image quality (WebP quality slider), max cached images, prefetch aggressiveness, CDN host selection. Currently the Performance tab in Settings appears to be a placeholder.
- **Why**: Users on limited bandwidth (or high-DPI monitors) need control over image quality vs. data usage. Power users want to tune the prefetch behavior.
- **Impact**: Low-Medium — power-user feature
- **Effort**: Small
- **How**: Extend `settingsStore` with `imageQuality: number` (0.1-1.0), `maxCacheEntries: number`, `prefetchEnabled: boolean`. Pass these as parameters to the image cache service. Wire into SettingsPage Performance tab.
- **Prerequisites**: Suggestion #13 (to show results of toggles)

## Layout

### 15. Sidebar Collapse + Dock Mode
- **What**: Persist sidebar collapse state, add an auto-collapse mode (collapses to icon-only dock when not hovered), and support mouse-over expand. The `sidebarCollapsed` prop already exists in Sidebar.tsx but the UI toggle is hidden/not prominent.
- **Why**: On 1366×768 laptop screens (common for gaming laptops), the sidebar at 18rem (288px) takes ~21% of horizontal space. Collapsed sidebar with hover-expand gives more room for the game grid while maintaining one-click nav access.
- **Impact**: Medium — improves usable screen real estate
- **Effort**: Small
- **How**: Persist `sidebarCollapsed` in `uiStore`. Add a collapse/expand chevron button at the sidebar bottom. Implement hover-expand: on mouse enter (collapsed state), expand to full width with AnimatePresence. On mouse leave with no click, collapse after 500ms delay.
- **Prerequisites**: None

### 16. Grid Density Settings (Compact / Comfortable)
- **What**: Implement the `compactMode` toggle from `settingsStore` — reduce card padding, gap, and font size in grid views. Currently the setting exists in the store but no UI components react to it.
- **Why**: Users with large libraries want denser grids (more games visible per scroll). New users want spacious comfortable mode. This is a zero-cost toggle that improves UX for both camps.
- **Impact**: Medium — high perceived value for low effort
- **Effort**: Small
- **How**: Wire `compactMode` from `settingsStore` into GameCard, LibraryCard, and grid containers. In compact mode: reduce card padding from `p-3` to `p-1.5`, gap from `gap-4` to `gap-2`, font size from `text-sm` to `text-xs`, cover image 85% size. Use Tailwind CSS class switching.
- **Prerequisites**: None

### 17. BrowsePage Layout for Smaller Windows
- **What**: Make BrowsePage responsive to window resize. Currently the layout assumes a fixed large viewport. Use `useMeasure` or a ResizeObserver to adapt column count, font sizes, and hero visibility.
- **Why**: Electron windows are resizable. When the user shrinks the window, cards overlap, text truncates poorly, and the layout breaks below ~1024px.
- **Impact**: Medium — robustness and polish
- **Effort**: Small
- **How**: Add a ResizeObserver to BrowsePage that adjusts HTML grid `cols-*` classes based on container width (not viewport media queries). At <800px: single column. At 800-1100px: 2 columns. 1100-1400px: 3 columns. 1400px+: 4+ columns. This uses container queries via JS or CSS `@container`.
- **Prerequisites**: None
